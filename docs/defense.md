# Подготовка к защите

## Короткое объяснение проекта

Программа хранит рейсы, пассажиров и билеты в SQLite. Через консоль можно
добавлять и изменять данные, искать записи, бронировать и отменять билеты.
При бронировании проверяются место и наличие другого билета у пассажира
на этот рейс. Статистика и текстовый отчёт строятся из сохранённых данных.

Если защита на английском, можно начать так:

> Our project is a console airline reservation system. It stores flights,
> passengers and tickets in SQLite. Users can manage records, search for
> passengers and destinations, book seats and cancel tickets. The program
> checks booking conflicts and calculates ticket revenue and seat occupancy.

Дальше показывайте действия в программе и объясняйте их своими словами.

## Как устроен код

`main.py` отвечает за общение с пользователем. `read_text()` проверяет пустой
ввод, `read_number()` повторяет запрос до положительного целого числа.
Функции подменю собирают поля и вызывают методы `AirlineSystem`.
Ошибки выводятся в консоль, после чего меню продолжает работу.

`airline.py` содержит класс `AirlineSystem`. Здесь проверяются форматы полей,
связи, занятость мест и допустимость изменений. Методы не спрашивают ввод
у пользователя, поэтому их можно проверять отдельно от меню.

`database.py` содержит класс `Database`. Он открывает соединение, включает
внешние ключи, создаёт таблицы и выполняет SQL. `seed()` добавляет учебные
данные только в полностью пустую базу. `close()` закрывает соединение.

Пример пути одного действия:

```text
main: пункт 1 → тип 3 → ticket_input(system)
  → AirlineSystem.add_ticket(flight_id, passenger_id, seat)
  → check_booking(): рейс, пассажир, диапазон места, конфликты
  → Database.execute(): INSERT INTO tickets ...
  → commit → сообщение с ID билета
```

Схема связей:

```text
flights.id     1 ─── много tickets.flight_id
passengers.id  1 ─── много tickets.passenger_id
```

Билет содержит ID рейса и пассажира. Поэтому имя пассажира не копируется
в каждый билет, а отображается через `JOIN`. Отдельная запись билета
связывает одного пассажира с одним рейсом и местом.

пригодны для сдачи:

```bash
python3 main.py --database rehearsal.db
```

## Вопросы по коду

**Почему два класса?** `Database` работает с хранением, а `AirlineSystem`
решает, допустимо ли действие. Меню отдельно, чтобы не смешивать ввод и SQL.

**Что такое `self`?** Ссылка на текущий объект. Например,
`self.database` хранит базу, переданную конкретному объекту `AirlineSystem`.

**Чем ID отличается от номера рейса?** ID — внутренний числовой ключ записи.
Номер вроде `KC900` — поле, которое видит пользователь. В этой модели номер
уникален: повторные вылеты под одним номером отдельно не моделируются.

**Почему нужны внешние ключи?** Нельзя создать билет с несуществующим рейсом
или пассажиром. Для SQLite проверку нужно включить через
`PRAGMA foreign_keys = ON` в каждом соединении.

**Как защищено место от двойного бронирования?** Сначала `check_booking()`
проверяет конфликт. Дополнительно `UNIQUE(flight_id, seat)` не даёт базе
сохранить два билета на одно место. `UNIQUE(flight_id, passenger_id)`
запрещает второй билет тому же пассажиру на тот же рейс.

**Почему нельзя уменьшить вместимость до числа проданных билетов?**
Важен максимальный номер занятого места. Если продан один билет на место 50,
вместимость нельзя уменьшить до 49, даже если остальные места свободны.

**Почему цена есть и у рейса, и у билета?** У рейса — текущая цена,
у билета — цена бронирования. Повышение тарифа не меняет уже сохранённую
стоимость. При переносе на другой рейс берётся его текущая цена.

**Как считаются результаты?** Выручка — `SUM(price)` из `tickets`.
Заполняемость — число билетов / сумма мест всех рейсов × 100.
`COALESCE(..., 0)` заменяет SQL `NULL` на ноль для пустых таблиц.
Перед делением также проверяется, что суммарная вместимость не равна нулю.

**Почему `COUNT(t.id)`, а не `COUNT(*)`?** При `LEFT JOIN` рейс без билетов
всё равно попадёт в результат. `COUNT(*)` посчитает эту строку,
а `COUNT(t.id)` пропустит `NULL` и вернёт правильный ноль.

**Почему для рейсов `LEFT JOIN`, а для билетов `JOIN`?** В списке рейсов нужны
и рейсы без бронирований. В списке билетов нужны соответствующие рейс
и пассажир; их наличие обеспечивают внешние ключи.

**Зачем `?` в SQL?** Значения передаются отдельно от текста запроса.
Например, кавычка в имени не становится SQL-кодом. Имена таблиц через `?`
передать нельзя, поэтому в `get_record()` есть список разрешённых таблиц.

**Что делает `with self.connection`?** При успехе сохраняет транзакцию,
при ошибке откатывает изменения. Соединение этот блок не закрывает;
его закрывает `close()` в `finally`.

**Зачем `casefold()`?** SQLite `lower()` не умеет менять регистр кириллицы.
В соединении зарегистрирована Python-функция `str.casefold`, которую SQL
использует для поиска по русским и казахским именам и городам.

**Что проверяет `re`?** Форматы номера рейса, email и даты. Для даты этого
недостаточно: `datetime.strptime()` отдельно отсекает 30 февраля и 25:00.
Проверка email проверяет форму адреса, а не существование почтового ящика.

**Зачем `random.Random(26)`?** Он выбирает вместимость, цены и пассажиров
для начальных билетов. Постоянное начальное значение даёт одинаковые данные
при создании пустой базы и позволяет повторить результаты демонстрации.

**Почему цены целые?** В проекте используются целые тенге. Это позволяет
считать деньги без погрешностей `float`. Проценты могут быть дробными;
для вывода они округляются до двух знаков.

**Что происходит при отмене?** Запись удаляется из `tickets`, место становится
свободным, сумма активных билетов уменьшается. История отмен и денежные
возвраты в этом проекте не реализованы.

**Какие ограничения у проекта?** Это локальная программа для одного оператора.
Нет авторизации, онлайн-оплаты, часовых поясов и истории операций. Прошедшие
даты допустимы; расчёты включают все сохранённые рейсы. Для одновременной
работы нескольких операторов потребовалась бы отдельная проверка транзакций.
